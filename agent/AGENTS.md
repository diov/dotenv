# AGENTS.md（用户级）

跨项目通用偏好。项目级规则写在项目根的 `AGENTS.md`，只写项目独有内容（技术栈、目录分层、命名边界、文档索引），不重复本文。

- 项目级 `AGENTS.md` 与本文冲突时以项目级为准。
- 有其他协作者的仓库，项目级 `AGENTS.md` 要自包含（协作者读不到本文），可以重复本文的规则。
- 项目里不放 `CLAUDE.md`、`.claude/CLAUDE.md`、`CLAUDE.local.md`：Claude Code 见到任何一个就不读 `AGENTS.md`，Codex 则只读 `AGENTS.md`。遇到旧项目还有 `CLAUDE.md`，提议合并进 `AGENTS.md` 后删除。

## 语言

- 规则、设计文档：中文；技术术语保留英文原词（KISS、breaking change、schema、commit）。
- 与我的对话：中文。包括工具调用之间的进度说明、提问、方案和总结；技术术语保留英文原词。
- 代码、标识符、注释、commit message、PR 描述：英文。
- 不要因为规则是中文就输出中文注释或中文 commit。

## KISS 优先

- 只做被要求的事：不加未被要求的功能、字段、配置项、fallback、UI 控件。
- 不过早抽象：相似代码不等于需要封装；只有一个实现时不抽 protocol / wrapper class。
- 不做防御性设计：只在系统边界（用户输入、外部 API）校验。
- 注释只解释"为什么"，不复述"做了什么"；逻辑自明的代码不加注释。
- 判据：今天从零实现当前语义，还会写出这段代码吗？答案为否就删。

## 依赖审核

- 优先级：**平台官方 > 生态事实标准 > 第三方 > 自己实现**。iOS/macOS 用 Apple 框架，Android 用 Google/JetBrains（AndroidX、Kotlin 官方库），Python 优先标准库。
- **引入任何新的第三方依赖前必须先问我**，并说明：官方方案为何不够、维护状态与许可证、能否用几十行自己实现。
- 简单工具类不引依赖；反过来，官方或现有依赖已提供的能力（手势识别、图标、序列化、限流）直接用，不要重造。

## 结构不对就重写

- 默认允许 breaking change；除非我说明已在生产环境，不为兼容性做妥协设计。
- 删除的代码直接删：不留别名、re-export shim、"旧版兼容"分支。
- 当前结构不适配需求时，先给"打补丁 vs 重写"的取舍让我选，不要默认打补丁。

## 流程档位

按改动风险选档，不按仓库大小选：

- **重流程**：命中任一条即走——数据模型或 schema 变更、跨模块改动、已在生产环境、改动对象有其他消费者（共享配置、对外 API）。
- **轻流程**：其余情况。
- 项目级 AGENTS.md 可声明默认档位；改动命中重流程条件时仍走重流程。拿不准就问我。

## 先方案后代码

- 设计、架构、数据模型、跨模块改动：**先给方案，不要给具体代码**，等我确认。
- 方案含：思路三句话、一个被否决的备选及理由、复用了哪个现有组件/入口、将改动的文件清单。
- 轻流程：方案在对话里给，不写计划文件。
- 重流程：实现计划写入文件（`task_plan.md` 或 `docs/plans/<name>.md`），按"一个 commit 一个意图"拆分；未批准不开始实现。
- 重流程计划的零上下文审查见 @~/.claude/claude-code-only.md
- 执行计划时，每完成一项就更新计划文档的状态和下一步；context 快不够时先写交接说明再停。
- 计划只放还要执行的内容：每个 session 都会重读计划，已完成的部分每次都白占 context。跨多个 PR（或多个 session）执行的计划，勾选进度时把完成的步骤（做法、执行记录、审查结果）原文移到归档（如 `docs/archive/<计划名>-done.md`），计划里只留勾选。移走前按「文档 → 测试 → 实现」把仍成立的结论并入现行文档；后续步骤要用到的规则写进现行文档或该步骤本身，不能只留在归档里。
- 大计划里需要单独审查的步骤（如重流程的子方案），方案写成独立文件，主计划对应的一行只留摘要和链接，完成后一起归档。
- 新建 UI 元素或命令前，先说明有没有现成入口可复用。

## 文档 → 测试 → 实现

- 实现前先读对应文档；文档是权威来源，不凭经验推断。文档与代码冲突时先确认以哪个为准。
- 语义变更顺序：先改 SPEC/schema/设计文档 → 再问哪些测试因此过期 → 最后改实现。
- 改完向回扫：旧语义遗留的中间推导、配置参数、冗余字段不会自己消失（且常有测试护着）。
- 实现改完同步更新受影响的文档。
- 计划或调研归档前，把仍然成立的结论并入现行文档（spec、规范、项目级 AGENTS.md）。现行文档不依赖归档：仍成立的结论写在现行文档里，引用归档只作为依据；归档只保留过程和决策理由。
- 项目知识（结论、实验结果、平台的坑、项目状态）和项目约定写进仓库文档，不写进 agent 的私有 memory；memory 只记不该提交进仓库的内容（只对我个人有效、不适合给其他协作者或公开仓库看到的）。

## 测试

- 判据：删掉被测函数的核心逻辑后测试仍通过，这个测试就是摆设，重写它。
- 测试描述业务期望，不约束实现细节；以业务为准，不为通过测试改业务代码。
- 不为测试保留生产参数：只有测试传非默认值的参数/开关，规则变更时一并删除。

## 一致性

- 同一概念只允许一种表示；出现两套命名/格式时先统一，不在代码里穿插。
- 要么全部支持默认值，要么全部显式传入，不要一半一半。
- 跨边界的命名转换（内部 snake_case ↔ 对外 camelCase）在边界层集中处理。
- 样式用语义 token，不留散落 hex 与魔法数字。
- 硬编码边界：部署/环境/跨端共享的值必须外置或由服务端下发；仅在验证阶段、单一取值、无第二消费者时可先写死并加注释。

## 结论要有依据

- 外部事实（API、券商功能、模型 ID、库版本）：先核实，标注 `[已验证 via 来源]` / `[未验证 — 可能过时]`。
- 量化结论（性能、换手、收益归因）：跑真实测量，不用代理指标推断；无数字支撑的说法标为假设。
- 架构选型：先给业内常见做法及来源，再给推荐。证据不足就说不确定。

## Git

- 不直接提交到 main：在分支上工作，给出 diff 摘要，确认后再合并。
- 破坏性命令（`git checkout -- <file>`、`reset --hard`、`clean`、强推）执行前先问我；需要保存现场用 stash。
- 提交、开分支或 worktree、合并、整理历史、删分支之前，以及任务收尾时，先读 skill `git-workflow`（原子 commit、worktree、合并与 review、整理历史、收尾清理的规则都在里面）。
- 长耗时后台任务（全量回测、批处理、全量转译）启动前先问我。
